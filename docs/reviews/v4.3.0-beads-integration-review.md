## Pass 1 Fixes (commit 16c7c23)

### Important

**[skills/executing-plans/SKILL.md:56]** Hardcoded label `br list --label superpowers` would silently miss every plan in any non-superpowers project.
- Why: This skill ships in a multi-project library — anchoring to a single label breaks portability the moment the user runs `/executing-plans` in a different project.
- Fix: Replaced fallback with `br dep tree <epic-id>` (parent-child traversal works regardless of label scheme), and pointed to the plan's "## Issue Tracking" appendix as the source of the epic ID.

**[skills/finishing-a-development-branch/SKILL.md:170-174]** `br close <id>` was issued unconditionally for every issue ID found in the merge range — but if `subagent-driven-development` already closed it earlier in the same merged batch, `br close` errors with "already closed" and aborts the loop.
- Why: Multi-skill workflows often pass through both SDD (which closes per-task) and finishing-a-development-branch (which closes per-merge). Without status gating, the second skill double-closes.
- Fix: Added `br show "$id" --json | jq -r '.status'` precheck and gated `br close` on `status=in_progress`. Also added the `br update` display-bug verification habit to the section.

**[docs/beads-integration-recommendations.md:96]** Recommendation block called `git log <merge-base>..HEAD --format=%H | xargs -I{} br orphans --commit {}` — but `br orphans` has no `--commit` flag (verified with `br orphans --help`).
- Why: The recommendation doc is the canonical reference future contributors copy from. A non-functional invocation here would propagate.
- Fix: Replaced with the explicit grep+close loop that mirrors what `finishing-a-development-branch` actually ships.

## Pass 2 Fixes (commit bc05b0c)

### Important

**[skills/finishing-a-development-branch/SKILL.md:173 + docs/beads-integration-recommendations.md:96]** Pass 1's introduced `jq -r .status` was silently broken — `br show <id> --json` returns a JSON **array**, not an object, so the filter always returned `null` and the `in_progress` check would never match. Net effect: the conditional close I added in Pass 1 would never have executed even one close.
- Why: Pass 1 fixed a real bug (unconditional close → "already closed" error) but introduced a new one (precheck always false → never closes). This is exactly the failure mode that motivates iterative re-review.
- Fix: Changed to `jq -r '.[0].status'` in both locations.
- Verification: `br show bd-ye2k --json | jq -r '.[0].status'` → `in_progress` ✓

**Lesson:** When testing fixes for a write-path bug, run the precheck against a known-state issue before committing. The Pass 1 fix would have lain dormant indefinitely (skills can run successfully without ever exercising the close path) until a future user hit it.

## Assessment
